# Екип от агенти

Спецификация на multi-agent организацията за разработка на Movie Tracker.
Това е durable референция — агентите и оркестраторът се ръководят от нея.

## Цел

Разделяне на работата по една итерация между специализирани агенти с **изолиран
контекст** и **ограничени инструменти**, така че:

- програмистът се концентрира само върху имплементацията (TDD),
- review-ът е **независим** и **не може да пише**,
- документацията спазва правилата на проекта (README в същия commit, single source of truth),
- а решенията за commit остават при потребителя.

## Защо оркестраторът НЕ е отделен агент

В Claude Code subagent-ите се пускат от главния loop и **не могат надеждно да пускат
други subagent-и** (влагането е едно ниво). Затова оркестраторът е **главната сесия**
(Claude, с който потребителят разговаря). Тя:

1. държи плана на итерацията,
2. делегира имплементацията на `mt-developer`,
3. подава diff-а на `mt-reviewer`,
4. при `APPROVE` подава на `mt-documenter`,
5. **спира и чака одобрение** преди commit (виж „Автономия").

## Роли

| Роля | Агент / примитив | Инструменти | Модел |
|------|------------------|-------------|-------|
| Оркестратор | главната сесия (не файл) | всички | Opus |
| Програмист | [`mt-developer`](../.claude/agents/mt-developer.md) | Read, Write, Edit, Bash, Glob, Grep | Opus |
| Code review | [`mt-reviewer`](../.claude/agents/mt-reviewer.md) — **read-only** | Read, Grep, Glob | Opus |
| Документатор | [`mt-documenter`](../.claude/agents/mt-documenter.md) | Read, Write, Edit, Glob, Grep | Sonnet |

> `mt-reviewer` няма `Bash`/`Write`/`Edit` → **физически не може да модифицира кода**.
> Diff-ът му се подава от оркестратора (главната сесия пуска `git diff`), а той чете
> околните файлове за контекст чрез `Read`/`Grep`.

## Handoff протокол (последователен, не паралелен)

Workflow-ът на проекта е TDD-strict и последователен, затова веригата е:

```
План (оркестратор, plan mode)
   ↓
mt-developer  →  връща: списък променени файлове + резюме + статус на тестовете (task test)
   ↓
mt-reviewer   →  получава: diff + списък файлове
              →  връща: находки [severity, file:line, проблем, предложение] + verdict (APPROVE / REQUEST_CHANGES)
   ↓ (ако REQUEST_CHANGES → обратно към mt-developer)
mt-documenter →  получава: какво е имплементирано
              →  връща: кои docs са пипнати + резюме
   ↓
ПАУЗА за одобрение от потребителя
   ↓
commit (оркестратор или /git-janitor)
```

### Какво връща всеки агент

- **mt-developer:** Markdown списък на променените/новите файлове, едно-абзацно резюме на
  промяната, и резултат от `task test` (зелено/червено + кои тестове).
- **mt-reviewer:** структуриран списък находки със `severity` (blocker / major / minor / nit),
  `file:line`, описание, предложен fix; накрая **един verdict ред**: `APPROVE` или `REQUEST_CHANGES`.
- **mt-documenter:** списък на пипнатите docs + потвърждение, че README е синхронизиран
  (когато е приложимо) и че няма дублирани решения.

## Автономия (commit gating)

Оркестраторът **спира и чака изрично одобрение** след зелени тестове + `APPROVE` review,
преди да направи commit. Commit-ът се прави с `/git-janitor` или ръчно от оркестратора,
по конвенциите на проекта (conventional commits на български, без опасни файлове).

## Бъдеще: паралелизъм чрез Workflow

Сегашната верига е последователна. Ако се появи нужда от паралелна работа (напр.
review по няколко измерения едновременно, или масов рефакторинг по много файлове),
това е случай за **Workflow tool**-а (детерминистична оркестрация), не за ръчно влагане
на агенти. Изисква изричен opt-in и затова не е част от стандартния цикъл.
