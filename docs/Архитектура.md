## 1. Технологичен стек

## 4. База данни — схема

Схемата по-долу отразява **текущото състояние след всички миграции** (000001 initial + 000002 + 000003 + 000004 + 000005 + 000006 + 000007 — последната е само за данни, схемата не се променя). Реалните файлове са в `internal/db/migrations/` (embedded).

```sql
-- Таблица media: всяка медия (филм или епизод) е един запис
CREATE TABLE media (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    filename TEXT NOT NULL,                       -- "Godzilla.Minus.One...mkv"
    folder_relative_path TEXT NOT NULL,           -- "01_NewDownloads\Godzilla..."
    file_size_bytes INTEGER NOT NULL,
    current_status TEXT NOT NULL DEFAULT 'new',   -- enum: new|started|for_dnd (completed_* са махнати с миграция 000007, Бъг 27)
    on_disk INTEGER NOT NULL DEFAULT 1,           -- bool: 1 = на диска, 0 = липсва
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    file_created_at TIMESTAMP NULL,               -- дата на създаване на файла (миграция 000002); NULL за стари записи
    translation_type TEXT NOT NULL DEFAULT '',    -- '' (незададен) | sub | bg | orig (миграция 000003)
    for_deletion INTEGER NOT NULL DEFAULT 0,      -- bool: 1 = маркирана „за изтриване" (миграция 000004); независима от current_status
    UNIQUE(filename, file_size_bytes)             -- идентификация
);

CREATE INDEX idx_media_status ON media(current_status);
CREATE INDEX idx_media_on_disk ON media(on_disk);
CREATE INDEX idx_media_folder ON media(folder_relative_path);

-- Event log: всяко стартиране на медия
CREATE TABLE start_events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    media_id INTEGER NOT NULL REFERENCES media(id) ON DELETE CASCADE,
    started_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_start_events_media ON start_events(media_id);
CREATE INDEX idx_start_events_started_at ON start_events(started_at);

-- Event log: всяка промяна на статуса
CREATE TABLE status_changes (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    media_id INTEGER NOT NULL REFERENCES media(id) ON DELETE CASCADE,
    from_status TEXT,                              -- NULL при първоначално създаване
    to_status TEXT NOT NULL,
    changed_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_status_changes_media ON status_changes(media_id);

-- Състояние на дървовидния изглед (споделено между всички компютри)
CREATE TABLE tree_state (
    folder_path TEXT PRIMARY KEY,
    expanded INTEGER NOT NULL DEFAULT 0            -- 1 = expanded, 0 = collapsed
);

-- Запомнено състояние на лентата с филтри/сортиране (миграция 000005) —
-- един-единствен ред, споделен между всички компютри
CREATE TABLE ui_prefs (
    id            INTEGER PRIMARY KEY CHECK (id = 1),  -- гарантира единствения ред
    status_filter TEXT NOT NULL DEFAULT 'all',
    disk_filter   TEXT NOT NULL DEFAULT 'on',
    sort_filter   TEXT NOT NULL DEFAULT 'name',
    dir_filter    TEXT NOT NULL DEFAULT 'asc',
    q_filter      TEXT NOT NULL DEFAULT '',           -- текстът от полето „търси…"
    trans_filter  TEXT NOT NULL DEFAULT 'all',
    del_filter    TEXT NOT NULL DEFAULT 'all',
    folder_filter TEXT NOT NULL DEFAULT 'all',        -- основната папка (миграция 000006, Бъг 26); 'all' = без филтър
    updated_at    TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

**Денормализация:** Не пазим `last_started_at`, `start_count` и подобни — изчисляват се с агрегатни заявки от event таблиците (single source of truth).

**Statuses (enum):**
- `new` — Нова (автоматично)
- `started` — Стартирана (автоматично)
- `for_dnd` — За DnD (ръчно)

Стойностите `completed_both` / `completed_yanko` / `completed_liza` са премахнати (Бъг #27, миграция 000007) — остават само като история в `status_changes`. Защо завършените станаха `started` и защо `for_dnd` е статус, а не флаг — в „Лог на решенията" (Итерация 41).

## 6. Поток на основните операции

### 6.1 Стартиране на приложението

0. Ако в `os.Args` присъства `--version` / `-v` / `version` → отпечатва `Movie Tracker <version> (build <N>)` и излиза веднага (без сканиране или стартиране на сървър)
1. `os.Executable()` → определя локацията на `.exe`
2. Извежда disk root (`filepath.VolumeName(...)`) и app folder
3. Логва `slog.Info("Movie Tracker", "version", ..., "build", ...)` на stdout (конзолата) + лог файла — преди тежкото сканиране
4. Зарежда per-computer config (`%LOCALAPPDATA%\MovieTracker\config.toml`); ако VLC не е намерен на стандартно място и не е в config — UI ще покаже съобщение
5. **Backup на базата** — копира `movietracker.db` в `backup\<timestamp>_movietracker.db` и изрязва до последните 10 снапшота; при липсваща база (първи старт) стъпката се пропуска, при грешка приложението спира
6. Отваря/създава DB файла в app folder
7. `golang-migrate` мига DB до latest версия (forward-only)
8. **Сканира диска синхронно** (виж 6.2) и синхронизира резултатите в DB — стъпката е **блокираща**: сървърът не приема заявки, докато сканът не приключи
9. Стартира HTTP сървър (gin) на `localhost:8080` и в goroutine отваря браузъра на главната страница (`http://localhost:8080/`)

> **Бележка (код ↔ дизайн):** Сканирането **при старт** е синхронно ([cmd/movietracker/main.go](../cmd/movietracker/main.go) — `scanner.Scan` преди `r.Run`), за разлика от **ръчното** `POST /scan`, което върви в background goroutine ([internal/web/handlers.go](../internal/web/handlers.go) — `Scan`). На голям диск (хиляди файлове) startup-скан забавя първоначалното зареждане на UI. Ако това стане проблем — стартовият скан може да се изнесе в goroutine (UI се вдига веднага, скан тече на фон).

### 6.2 Сканиране на диска (алгоритъм)

> Синхронно при старт (стъпка 6.1.8); в background goroutine при ръчно `POST /scan`.

1. Обхожда top-level папки на диска
2. Прескача папки от exclude list (hardcoded в MVP-1)
3. Рекурсивно обхожда всяка папка (поддръжка на дълги пътища `\\?\`)
4. Индексира субтитърните файлове (`.srt`, `.sub`, `.ass`, `.ssa`, `.idx`, `.vtt`) по папка — нужни за авто-разпознаване на тип превод
5. За всеки видео файл (`.mkv`, `.avi`, `.mp4`):
   - Прилага Sample филтриране (под 50 MB в папка с по-голям видеофайл → пропуска)
   - Изчислява `(filename, file_size_bytes)` като ID
   - Изчислява подсказка за тип превод (виж по-долу)
   - INSERT/UPDATE в `media` (UPSERT по UNIQUE constraint)
6. Маркира всички непосетени `media` записи като `on_disk = 0`
7. При повторно намиране на файл → `on_disk = 1`

**Авто-разпознаване на тип превод (Bug #17):** при upsert типът се попълва **само
ако още е празен** (`translation_type = CASE WHEN media.translation_type != '' THEN ... ELSE excluded ... END`),
така че повторен скан не прегазва ръчния избор. Логика на подсказката:
- **`bg`** — името на видеофайла **или** relative папката съдържа `BGAUDIO` / `BG.AUDIO` (case-insensitive);
- **`sub`** — в същата папка има субтитър със същото базово име (или базово име, започващо с името на видеото + `.`);
- **Приоритет:** `bg` пред `sub`.

### 6.3 Стартиране на медия

1. Потребител кликва на медия → `POST /media/:id/start`
2. Backend INSERT-ва ред в `start_events` (записва event **безусловно**)
3. Backend конструира пълния път: `<disk_root>\<folder_relative_path>\<filename>`
4. `exec.Command(vlcPath, fullPath)` стартира VLC
5. Ако VLC fail-не → връща HTML fragment с грешка (но event-ът е записан)
6. Ако `current_status == 'new'` → UPDATE към `started` + INSERT в `status_changes`
7. Връща обновения HTML fragment за медията

### 6.4 Промяна на статуса

1. Потребител избира статус → `POST /media/:id/status`
2. Backend проверява статуса (виж §5 и „Statuses (enum)" в §4); друго → `400`, без промяна
3. Backend в трансакция:
   - UPDATE `media` SET `current_status = новия`
   - INSERT в `status_changes` (from_status, to_status, changed_at)
4. Връща обновения HTML fragment

### 6.5 Изваждане на диска

1. При следваща HTTP заявка → middleware проверява `os.Executable()`-я disk root е достъпен
2. Ако няма достъп → връща error page *"Дискът не е свързан..."*
3. При повторно свързване → user обновява страницата → нормална работа

## 7. Build / dev workflow

`Taskfile.yml`:

```yaml
tasks:
  install:
    desc: Инсталира dev зависимости
    cmds:
      - go install github.com/a-h/templ/cmd/templ@latest
      - go install github.com/sqlc-dev/sqlc/cmd/sqlc@latest
      - go install github.com/cosmtrek/air@latest
      - go install github.com/golangci/golangci-lint/cmd/golangci-lint@latest
      - go install github.com/evilmartians/lefthook@latest

  generate:
    desc: Генерира templ + sqlc код
    cmds:
      - templ generate
      - sqlc generate

  lint:
    cmds:
      - gofmt -l .
      - golangci-lint run

  test:
    desc: Стартира всички Go тестове (unit + integration + API)
    cmds:
      - go test ./...

  test:e2e:
    desc: Стартира browser E2E тестове (Python Playwright). Преди това стартира Go сървъра.
    cmds:
      - cd tests/e2e && pytest

  build:
    desc: Билдва статичен .exe в bin/ (автоматично увеличава build номера)
    vars:
      VERSION: v1.10.1
      BUILD:
        sh: go run ./cmd/bumpbuild   # чете/увеличава .build-number (gitignored)
    cmds:
      - go build -trimpath -ldflags "-s -w -X main.version={{.VERSION}} -X main.buildNumber={{.BUILD}}" -o bin/movietracker.exe ./cmd/movietracker

  run:
    desc: Стартира с hot reload
    deps: [generate]
    cmds:
      - air

  migrate-new:
    desc: 'Създава нова миграция: task migrate-new -- name'
    cmds:
      # ВАЖНО: -dir трябва да сочи internal/db/migrations — оттам приложението embed-ва (//go:embed)
      - migrate create -ext sql -dir internal/db/migrations -seq {{.CLI_ARGS}}
```

`-trimpath` и `-s -w` се прилагат само в production `build` (dev билдовете през `air`/`go run` запазват debug символите); намаляват `.exe`-то с ~31% — виж §10 „Защо exe е ~19 MB (и защо беше ~28 MB)" за пълния анализ.

## 8. Тестова стратегия

**Pyramid: unit + integration + API + frontend + manual**, прилагана и за MVP-1, и за MVP-2.

### Unit tests (бързи, без I/O)
- `scanner`: Sample филтриране, exclude logic, разпознаване на видео формати
- `media`: преходи на статуси, валидация
- `config`: TOML парсване
- `vlc`: detection logic, аргументи на команда

### Integration tests (с реална SQLite)
- `db`: sqlc заявки върху ad-hoc SQLite файл
- `db`: миграции с данни — схемата се спира на предишната версия (`internal/db/export_test.go` отваря `newMigrate` за пакета `db_test`), зарежда се seed и се пуска `Migrate` (напр. 000007)
- HTTP handler логика с `httptest` сървър (in-process, без мрежа)
- End-to-end backend flow: scan → start → mark status → query

### API request tests (HTTP-level)
Тестове, които правят реални HTTP заявки към `httptest.Server` и валидират пълния request/response цикъл:
- **Инструменти:** `net/http/httptest` + `net/http.Client` + `PuerkitoBio/goquery` за HTML парсване
- **Покритие:**
  - `GET /` връща HTML с правилен списък на медии
  - `POST /media/:id/start` записва event и връща обновен HTML fragment
  - `POST /media/:id/status` променя статуса и връща fragment
  - `POST /scan` стартира сканиране и връща статус
  - HTTP грешки (404 за невалидни ID, 400 за непознат или махнат статус, 500 при DB проблеми)
- **Асерции:** върху status code, headers, и **DOM елементи в HTML отговора** (чрез goquery — напр. *"трябва да има `<tr>` за всяка медия", "статусът се вижда в правилната колона"*)

### Frontend tests (browser E2E)
Тестове на цели UI workflow-и в реален headless browser:
- **Инструмент:** **Python 3.13 + `pytest-playwright`** (официалният Microsoft Playwright за Python). Тестовете се пишат в Python, а не в Go — отделна тестова екосистема.
- **Защо Python Playwright (а не Go bindings):** официалната версия е по-зряла, има codegen, trace viewer, и пълна функционалност. Python вече е инсталиран на машината.
- **Структура:** тестовете живеят в `tests/e2e/` с собствен `pyproject.toml`. Стартират се чрез `task test:e2e`, който вдига Go сървъра и пуска `pytest`.
- **Покритие на критичните потоци:**
  - Смяна на статуса на медия (напр. към "За DnD") → проверка че статусът се обновява в UI
  - Стартиране на медия → проверка че запис се появява в историята (VLC се мокна или процесът се прекъсва)
  - Превключване между плосък списък и дървовиден изглед (MVP-2)
  - Филтриране по статус → проверка че списъкът се филтрира
  - 🎲 стартиране на случайна медия → под лентата се изписва „🎲 Стартирах: …" и редът на избраната медия се обновява на място (HTMX OOB swap; виж „Лог на решенията", Итерация 42)
- **Тестовете са по-малко на брой** (5-10), но покриват HTMX swap behavior и UI consistency, които HTTP-only тестовете не виждат
- **Auto-waiting** на Playwright прави тестовете стабилни без `sleep()`
- **⚠️ Ограничения на текущия harness (важно):** [tests/e2e/conftest.py](../tests/e2e/conftest.py) билдва exe в repo root и го стартира, затова приложението определя `DiskRoot` = волуума на repo-то (на dev машина обикновено **системния диск**) и **сканира реалния диск** — няма изолиран/seeded тестов диск. Последици: тестовете зависят от реалното съдържание на диска (недетерминирани), интеракционните тестове стартират **истински VLC** и мутират DB, построена от реалните файлове. Освен това стартовият скан е синхронен (виж 6.1.8) и сървърът започва да слуша едва след него, затова `_wait_for_server` timeout-ът трябва да покрива целия скан — зададен на **120s**. На dev машината скенът обхожда реалния системен диск и вече трае **~45s** (по-рано ~5–10s + overhead): растящото съдържание на диска изпревари предишните 30s, а при изтекъл таймаут фикстурата `live_server` хвърля грешка и **всички** e2e тестове завършват с error (още по-старите 10s падаха при студен FS кеш). 120s е резерв, а не решение — времето следва размера на диска, затова чистото решение за в бъдеще остава env var (напр. `MOVIETRACKER_DISK_ROOT`) за override на сканирания корен + seeded тестова папка с фиктивни видео файлове.

## 10. Лог на решенията (обосновки)

Кратки обосновки за ключовите архитектурни избори, които може да са нетривиални за бъдещи разработчици.

### Защо `.exe` живее на диска (а не на компютъра)
Дискът пътува между 3 компютъра. Ако `.exe` беше на компютъра, трябваше да се поддържа отделна инсталация на всеки от тях + механизъм за намиране на диска (буква, маркер). С `.exe` на диска: едно място, нула per-computer инсталация, естествено разпознаване чрез `os.Executable()`.

### Защо идентификация по `(filename, file_size_bytes)`
Алтернативи: пълен път (чупи се при преместване на филм), хеш (бавен при хиляди файлове). Името+размерът дава баланс — устойчиво към преместване в друга папка на диска, бързо.

### Защо event log в **две** отделни таблици (`start_events` + `status_changes`)
Алтернатива: една полиморфна `events` таблица. С две таблици: type-safe (sqlc генерира различни типове), четливи заявки, без `event_type` поле + nullable колони. При само два типа събития, полиморфизмът е overengineering.

### Защо `current_status` е денормализирана колона в `media`
Алтернатива: винаги се изчислява от последния `status_change`. С денормализация: бързи UI заявки + прости филтри по статус. Дублирането се поддържа в трансакция (UPDATE media + INSERT в status_changes), което прави consistency проблема managed.

### Защо UI denormalization (last_started_at, count) се **изчислява**
Single source of truth (event таблиците) → по-малко bug-ове за консистентност. SQLite се справя без проблем при ~1000 записа. Може да се добави денормализация по-късно ако стане bottleneck.

### Защо forward-only миграции (без version check)
`.exe` живее на диска → има само един източник на истина за версията. Downgrade сценарий е практически невъзможен. Forward-only е стандарт на `golang-migrate` и опростява кода (без version checks, без блокиране).

### Локация на миграциите: `internal/db/migrations/`
Миграциите се embed-ват с `//go:embed migrations` от [internal/db/database.go](../internal/db/database.go) → каноничната им локация е **`internal/db/migrations/`** (пълният списък на миграциите — в §4). Top-level `migrations/` е остаряло копие (само 000001) — **DEPRECATED, да се изтрие**. `task migrate-new` създава именно в `internal/db/migrations` (виж §7); подаване на грешна `-dir` би сложило новата миграция в папка, която приложението не чете.

### Защо hardcoded статуси (вместо конфигурируеми)
Алтернативa: таблица `users` + връзка media-user-watched (поддържа N потребители). За 2 потребителя hardcoded enum-ът е по-прост, type-safe (sqlc генерира Go константи), и достатъчен за дългосрочната визия. Добавяне на трети потребител в бъдеще = code update + DB миграция (приемлив компромис за рядко събитие).

*Бележка (Итерация 41):* статусите вече не са по потребител — `completed_*` са премахнати (виж „Защо завършените статуси се махат с data миграция, а не само от интерфейса" по-долу); изборът на фиксиран набор остава в сила.

### Защо `modernc.org/sqlite` (вместо `mattn/go-sqlite3`)
mattn е по-зрял и бърз, но изисква CGo (C компилатор за билд). modernc е pure Go → статичен binary без external dependencies. Performance разликата (~10-30%) е незабележима при нашия размер.

### Защо tree_state в БД (а не в per-computer config)
Първоначално планирано в локалната конфигурация. Промяна на курса: централно в БД на диска → споделено между компютрите. По-прост модел, по-малко конфигурация, естествено за use case (пробабилно се ползва един основен компютър).

### Защо няма авто-стартиране (AutoPlay)
Реализацията на Windows AutoPlay registration изисква registry edits + COM API. Сложно за минимална стойност. Потребителят винаги може ръчно да кликне `.exe` от диска.

### Защо HTMX (вместо REST API + SPA)
За локално приложение с прост UI няма нужда от SPA (React/Vue/Svelte). HTMX дава достатъчна интерактивност с server-rendered HTML, без build pipeline за JS, без отделен frontend codebase.

### Защо сортиране по дата на файла (а не `created_at` от DB)
`created_at` отразява кога скенерът е открил файла — зависи от кога потребителят е стартирал приложението, не кога файлът е поставен на диска. Windows `syscall.Win32FileAttributeData.CreationTime` дава реалната дата на създаване на файла. Тъй като приложението е Windows-only, нямаме нужда от cross-platform абстракция. Стойността се съхранява като `file_created_at` в DB (попълва се при сканиране), с fallback към `created_at` за записи преди тази миграция.

### Защо build изходът винаги е в `bin/`
Всички `task build` артефакти отиват в `bin/movietracker.exe`, а не в корена на проекта. Държи root-а чист, отделя build изхода от изходния код, и дава едно предвидимо място за намиране на binary-то преди копиране на диска. Папката `bin/` е в `.gitignore` (покрита и от `*.exe`). Конвенцията важи и за бъдещи build цели.

### Очакван размер на DB файла (детайлна оценка)
- Таблица `media` (~1000 записа × ~300 байта/ред) → ~300 KB
- Таблица `start_events` (~100/година × 5 години × ~50 байта) → ~25 KB
- Таблица `status_changes` (~500 промени × ~80 байта) → ~40 KB
- Таблица `tree_state` → ~50 KB
- Индекси, метаданни → ~200 KB
- **Общо: под 1 MB при 5-годишно ползване**

Изискване в заданието: под 5 MB (с резерв за растеж).

### Защо отделни `master` (продукшън) и `develop` (разработка) бранчове
До v1.0.0 цялата работа течеше директно в `master` — нямаше разгърната версия за пазене. След пускането на v1.0.0 в продукшън `master` трябва да остане стабилен и да отразява точно разгърнатото. Затова новите функции вече се разработват в `develop` и се сливат в `master` само при релийс (с нов таг). Лек git-flow, подходящ за малък екип и едно продукшън разгръщане. Каноничната референция към продукшън състоянието е тагът (`v1.0.0`), не върхът на `master`.

### Защо 🎲 ползва HTMX OOB swap вместо full-page redirect (Итерация 24)
`POST /media/random-new/start` пренаписва само два фрагмента: flash съобщение (`#flash`) и единствения засегнат ред (`<tr hx-swap-oob="true" id="media-{id}">`). Алтернативата — redirect към `GET /` с query параметрите — презаре жда цялата страница и нулира scroll позицията, което е неудобно когато избраният ред е извън видимия прозорец. OOB swap дава същата коректност при значително по-малко ефект върху UI. Без HTMX (graceful fallback) redirect с query параметрите остава.

*Бележка (Итерация 42):* в тази си форма (флаш първи, ред втори) отговорът не е обновявал реда в браузъра; подредбата, която работи, и защо — в „Защо 🎲 отново изписва избраната медия …" по-долу.

### Защо `RandomNew` сменя статуса само при `new → started` (Итерация 24)
Ако `RandomNew` смени статус безусловно (напр. `completed_yanko → started`), филмът изпада от активния филтър веднага след OOB swap — потребителят вижда ред с различен статус от очаквания и навигацията се обърква. Правилото е идентично с `StartMedia`: `InsertStartEvent` е безусловен; UPDATE към `started` се прави само ако текущият статус е `new`. Вече-завършените филми запазват статуса си, остават в активния филтър и редът им се обновява на място.

*Бележка (Итерация 41):* `completed_*` вече не съществуват; правилото се пази за ръчния статус `for_dnd` (виж „Защо „За DnD" е статус, а не флаг" по-долу).

### Защо версията се инжектира с ldflags (а не с `//go:embed`) (Итерация 25)
`//go:embed` на файл версия би означавало да има проследяван файл, чиито байтове се сменят при всеки билд — или да се embed-ва gitignored файл (невалидно: Go embed не поддържа gitignored пътища). ldflags `-X main.version` / `-X main.buildNumber` инжектира стойностите директно в binary без никакъв допълнителен файл в хранилището. Резултатът е идентичен статичен binary без CGo зависимости.

### Защо build номерът е gitignored per-machine брояч (а не git commit hash) (Итерация 25)
Git commit hash е непрактичен като „build номер": не е монотонен, не е кратък, и се мени само при комит (при повторен билд на едни и същи сорсове дава един и същ hash). Монотонен брояч в `.build-number` нараства при всеки `task build` — подходящо за локално, single-developer приложение, разгърнато на личен диск. Файлът е gitignored (без git churn), per-machine (различните машини имат независими брояча, което е приемливо за некритичен debugging идентификатор). При чисто клониране файлът липсва; `cmd/bumpbuild` третира липсващия файл като `0` → първи билд = `1`.

### Защо авто-преводът се попълва само при празна стойност (Итерация 29)
Сканирането минава периодично; ако разпознаването прегазваше `translation_type`
безусловно, един ръчно поправен от потребителя тип (или предишно разпознат) щеше да
се връща при всеки скан. Затова `UpsertMedia` пише разпознатата подсказка само когато
текущата стойност е празна (`CASE WHEN media.translation_type != '' THEN ... ELSE excluded`).
Така автоматиката е „помощник за първоначално попълване", а не източник на истина,
който се бори с потребителя.

### Защо БГ има приоритет пред СУБ при авто-разпознаване (Итерация 29)
Филм с български дублаж (`BGAUDIO` в името/папката) е „БГ" дори когато до него стои
субтитърен файл — българският говор е по-силният и по-рядък сигнал, а субтитри често
съпътстват и дублирани копия. При едновременни сигнали затова се записва `bg`.

### Защо exe е ~19 MB (и защо беше ~28 MB) (Итерация 35)
Production `.exe` тежеше 28 934 144 байта (27.6 MiB). По принос на размера: (1) `modernc.org/sqlite` + `modernc.org/libc` (~10-15 MB, доминиращ дял) — цената на решението за pure-Go SQLite без CGo (виж „Защо `modernc.org/sqlite`" по-горе), не е дефект; (2) symbol table + DWARF debug информация, разпространявана в production binary без полза за потребителя; (3) Go runtime (~1.5-2 MB); (4) `gin` + `validator` + `bytedance/sonic`; (5) embedded ресурси (Pico.css, HTMX, миграции) — само ~133 KB, пренебрежимо. Библиотеки като `quic-go` и `mongo-driver`, видими в `go.mod` (транзитивни на `golang-migrate`), не влизат в крайния binary — dead-code elimination на линкъра премахва неизползвания код; `mattn/go-sqlite3` е зад CGo build tags и не се компилира при `CGO_ENABLED=0`. Production `task build` вече компилира с `-trimpath -ldflags "-s -w -X ..."` — измерено намаление 28 934 144 → 19 888 128 байта (−31.3%); dev билдовете (`air`, `go run`) не прилагат тези флагове и запазват debug символите за по-удобно трасиране. Разгледани и отхвърлени алтернативи: **UPX компресия** (~9-12 MB) — по-бавен студен старт и риск от anti-virus false positives, неприемливо за `.exe`, който пътува на преносим диск между 3 компютъра; **връщане към `mattn/go-sqlite3`** — би реверснало вече документираното решение за статичен binary без CGo заради несъществена performance разлика. Дългосрочният под от ~19 MB е присъщ на pure-Go SQLite стека.

### Защо backup на базата преди миграциите и защо се пазят 10 снапшота (Итерация 36)
Базата е единственият носител на историята (кой филм е гледан, кога, с какъв статус) — дискът може да бъде изваден по време на запис, миграция може да се окаже дефектна, файлът може да се повреди. Затова при **всеки** старт се прави копие. Копието се прави **преди** `db.Open` и `db.Migrate`: така снапшотът е предмиграционното състояние — точно това, към което потребителят би искал да се върне, ако нова версия развали схемата (миграциите са forward-only, няма `down`). Понеже файлът още не е отворен от процеса и не се ползва WAL режим, обикновено файлово копие е консистентно — не е нужен `VACUUM INTO` или SQLite backup API. **Задържане 10:** базата е под 1 MB (виж „Очакван размер на DB файла“), т.е. 10 копия са ~10 MB — нищожно за преносим диск, но достатъчна дълбочина, за да се стигне до състояние отпреди няколко стартирания. Неограничено пазене би натрупало ~365 файла на година без полза. Изрязват се само файлове с валиден timestamp + името на базата, за да не се трият ръчни копия в същата папка. **При провал стартирането спира** (`os.Exit(1)`) — по изрично решение на потребителя: по-добре видима грешка, отколкото тиха работа без резервно копие.

### Защо „за изтриване" е отделен флаг и отделен параметър `del`, а не статус (Итерация 37)
Първата очевидна реализация би била нова стойност на `current_status` (`for_deletion` до `new`/`started`/`completed_*`). Отхвърлена е, защото статусът е **едностойностен**: маркирайки филм за изтриване, той щеше да загуби информацията, че е гледан и от двамата — точно данните, заради които приложението съществува. „За изтриване" е ортогонално на гледането: най-типичният кандидат за чистене е именно завършен филм. Затова е **булева колона** `for_deletion` (миграция 000004) и **отделен query параметър** `del=all|yes`, който се комбинира със `status`, `disk`, `q` и `trans` вместо да ги изключва (`/?status=completed_both&del=yes` = „завършени и маркирани"). Бутонът обаче се рендира **вътре в съществуващата група `.filter-btns`** — по изричното желание на потребителя лентата да не расте с нова група; същият похват вече се ползва от дисковия toggle `↕`, който също е отделен параметър в тази група. Филтърът е двупозиционен (всички ⇄ само маркираните); трета стойност „само немаркираните" не е въведена, защото това е състоянието по подразбиране. Флагът не се пипа от `UpsertMedia`, така че повторно сканиране на диска го запазва.

*Бележка (Итерация 41):* `completed_*` са премахнати, а „За DnD" е въведен като **статус** — разликата е обяснена в „Защо „За DnD" е статус, а не флаг" по-долу; решението за `for_deletion` остава непроменено.

### Защо запомненото състояние на филтрите е една таблица с един ред (Итерация 38)
Състоянието на регистъра (`status`, `disk`, `sort`, `dir`, `q`, `trans`, `del`) досега живееше само в URL-а и се губеше при всяко пускане на `.exe`-то. Пази се **в базата, на диска** — не в `%LOCALAPPDATA%` и не в браузърски `localStorage` — по същата логика като `tree_state`: настройката е на *колекцията*, следва диска между трите компютъра и оцелява при смяна на браузър. Схемата е **фиксирана таблица с един ред** (`ui_prefs`, `id INTEGER PRIMARY KEY CHECK (id = 1)`), а не key-value: наборът е малък и известен, така четенето е един ред с типизирани колони, без сериализация и без „липсващ ключ" като състояние. Редът се създава от самата миграция, затова `GetUIPrefs` винаги намира ред. Запомненото се ползва като **default на всеки query параметър поотделно** (`c.DefaultQuery("status", prefs.StatusFilter)`), а не като специален случай „голо `/`" — изричният URL винаги бие запомненото, а всички линкове в лентата и без това носят и седемте параметъра. Записът става при всяко успешно `GET /` (включително HTMX заявката на живото търсене) — един UPSERT на един ред е пренебрежим до без друго правените заявки за списъка. Грешка при четене пада към константите по подразбиране, грешка при запис само се логва: запомнянето е удобство и не бива да чупи страницата. **Текстът от търсенето също се помни** — изрично решение на потребителя: списъкът трябва да изглежда точно както е оставен. Следствие за тестовете: e2e сесията дели един сървър и една база, затова `tests/e2e/conftest.py` връща състоянието към default-ите преди всеки тест.

### Защо пускането на външни програми минава през `Launcher`, а `nil` не пуска нищо (Итерация 39)
`StartMedia`, `RandomNew` и `OpenFolder` викаха `exec.Command(...).Start()` директно. За `OpenFolder` това беше **безусловно**, затова всяко `task test` отваряше два Explorer прозореца, а e2e свитата (истински binary с открит VLC) отваряше VLC при всеки клик върху име на файл и браузър при всяко стартиране на сървъра. Решението не е триене на тестовете (това би загубило покритие), а инжектиране: `Handlers.Launcher` е `func(name string, args ...string) error`. Ключово е коя стойност е по подразбиране — **`nil` означава „не пускай нищо"**, а не „пусни наистина". Така тест, който забрави да подаде launcher, физически не може да отвори прозорец; реалният `ExecLauncher` се задава на едно-единствено място (`main.go`). Обратната подредба (nil = exec) би оставила капана отворен за всеки бъдещ тест. Цената е, че конструиране на `Handlers` в продукцията без launcher би спряло VLC тихомълком — приемлива, защото конструкторът е един. За e2e, където се пуска истинският binary, служи променливата **`MOVIETRACKER_NO_LAUNCH=1`** (`web.NoLaunch()`): подменя launcher-а с `NoopLauncher` и пропуска `openBrowser`. Избран е env флаг, а не CLI аргумент, защото `conftest.py` така или иначе стартира процеса през `subprocess.Popen` и подаването на `env` е по-малко инвазивно от нов публичен флаг на потребителския `.exe`. Грешка от launcher-а само се логва (`Warn`) — страницата трябва да се рендира и когато VLC липсва.

### Защо падащото меню за папка се пълни от данните и праща цялата форма за търсене (Итерация 40)
Бъг #26 назовава `Movies`, `MoviesDnD` и `Serials`, а §3 още описва по-стара подредба (`00 Yanko` … `99 Гледани`) — подредбата на диска вече се е сменяла, затова опциите **не са зашити в кода**, а са различните основни папки (първият сегмент на `folder_relative_path` до `\` или `/`) на медиите в базата: нова или преименувана папка се появява без промяна на кода. Сравнението е точно (`Movies` ≠ `MoviesDnD`), а файл директно в корена няма основна папка и се вижда само при „всички папки". Опциите се строят от медиите на текущия режим `↕` (на диска / всички), но **преди** останалите филтри: ако се строяха след тях, избор на статус, превод или текст за търсене би скривал папки, менюто би „скачало" и потребителят не би могъл да превключи директно към друга папка; `↕` обаче сменя самото множество от медии, затова папка само с изчезнали медии се появява едва при `disk=all` — в съгласие със списъка, който се вижда. Менюто **не е нова форма**: `<select form="search-form">` е закачено чрез HTML атрибута `form` за формата за търсене, която така или иначе носи скритите `status/disk/sort/dir/trans/del` и `q` — втора форма би дублирала скритите полета на всички филтри. Смяната на папка прави **пълно GET презареждане**, а не HTMX swap: живото търсене сменя само `#media-list`, а href-овете в лентата и скритото `folder` на 🎲 стоят извън него и трябва да се пререндерират с новата папка; самото живо търсене носи `folder`, защото `hx-include="closest form"` събира `form.elements`, а те включват и контролите, свързани чрез `form`. Стойността минава през **`url.QueryEscape`** (`folderParam`), защото имената идват от диска и не са под наш контрол — интервали, кирилица (`99 Гледани`), възможни `&` и `#`. **Запомнената папка, която вече я няма, остава в менюто и е избрана** — принципът е същият като в [Гранични случаи #9](Гранични%20случаи.md): тиха подмяна с „всички папки" би скрила, че филтърът действа, а изчезването ѝ от менюто би оставило празния списък необясним. Последният проблем е **back/forward cache**: `<select>`-ът се сменя, преди `form.submit()` да напусне страницата, затова при Back браузърът я възстановява с новата папка върху стария списък. Поправката е inline `pageshow` слушател, който при `e.persisted` само връща менюто към опцията, която сървърът е отрисувал (`option[selected]`). **Презареждането е отхвърлено:** `location.reload()` зарежда наново адреса от адресния ред, а за голо `/` (началната страница на сесията, линковете „Списък", redirect-ите след POST) сървърът рисува запомненото състояние от `ui_prefs` — което току-що напуснатата страница вече е презаписала; Back би изглеждал сякаш не прави нищо, и то за **всеки** филтър, не само за папката. Цената е същата като при всеки филтър от Бъг #23: след Back `ui_prefs` пази по-новата папка, докато следващ клик или търсене не запише състоянието наново.

### Защо завършените статуси се махат с data миграция, а не само от интерфейса (Итерация 41)
Бъг #27 махна `completed_both`, `completed_yanko` и `completed_liza`. Само махане на бутоните, филтрите и етикетите не стига: редовете в `media` с тези стойности остават, а `statusShort`/`statusClass` рендират всяка непозната стойност като „Нова" — гледан филм щеше да изглежда нов, но филтърът ○ (точно сравнение с `new`) не би го намирал. Затова се мигрират данните, а не само интерфейсът. Миграция **000007** прави три неща. (1) За всяка завършена медия **вписва ред в `status_changes`** (`completed_* → started`) — така историята остава в съгласие с `current_status` (консистентността от „Защо `current_status` е денормализирана колона в `media`"), а старата стойност не се губи, а остава като `from_status`. (2) Сменя `current_status` на `started` — **по решение на потребителя**: „Стартирана" е най-близкото останало състояние за филм, който вече е гледан, докато „Нова" би означавало, че не е пускан. (3) **Нулира `ui_prefs`**, ако запомненото сочи към махнатото: `status_filter` със завършен статус става `all`, а `sort_filter = 'marked'` — `name`/`asc`. Без това след рестарта лентата би показала празен списък (или сорт по име) без нито един активен бутон — проблемът от [Гранични случаи #9](Гранични%20случаи.md), който тук се предотвратява при източника; другите запомнени избори не се пипат. Миграцията е само за данни — схемата в §4 не се променя. **`down` е no-op** (`SELECT 1`): миграциите са forward-only (виж „Защо forward-only миграции (без version check)"), а пътят назад са backup-ът, който се прави преди миграциите (Итерация 36), и историята в `status_changes`. Миграцията чисти само вече записаното, затова **`ChangeStatus` приема само статусите от §4** (`400` за друго; allowlist-ът замени и старата проверка за празен статус) — иначе стара форма, стар таб или ръчна заявка биха записали `completed_*` отново, а `statusShort` би го показал като „Нова". Стари адреси в историята на браузъра със `status=completed_*` или `sort=marked` не се нормализират — виж [Гранични случаи #11](Гранични%20случаи.md).

### Защо „За DnD" е статус, а не флаг (Итерация 41)
Бъг #27 иска „нов статус и филтър - За DnD" и това е изпълнено буквално: `for_dnd` е стойност на `current_status`, избира се със същите бутони като другите статуси, филтрира се през съществуващия параметър `status` (бутон `D` в групата „филтър:") и не изисква нова колона, нов параметър или промяна на схемата. Това е **обратното** на решението за „за изтриване" (виж „Защо „за изтриване" е отделен флаг и отделен параметър `del`, а не статус (Итерация 37)"), където статус беше отхвърлен, защото е едностойностен и маркирането би изтрило информацията „гледан от двамата". Този разход днес го няма: с махането на `completed_*` статусът вече не пази „кой е гледал", което втора стойност да презапише, а потребителят изрично поиска статус. Цената на избора е следствие от него: медия не може да е едновременно „Стартирана" и „За DnD" — за разлика от флага `for_deletion`, който стои върху всеки статус. За да не се губи ръчният избор тихо, `for_dnd` следва правилото на бившите завършени статуси (виж „Защо `RandomNew` сменя статуса само при `new → started` (Итерация 24)"): `StartMedia` и `RandomNew` сменят само `new → started`, затова медия „За DnD" остава „За DnD" и след стартиране.

### Защо „Стартирана N пъти" стана точно: заявката за статистика вече не join-ва `status_changes` (Итерация 41)
`FetchMediaStats` и `FetchSingleMediaStats` смятаха `COUNT(se.id)` върху `media LEFT JOIN start_events LEFT JOIN status_changes`; вторият join съществуваше само за `marked_at` — датата на последния преход към завършен статус, нужна за сорта „по дата завършване". Два независими 1:N join-а в една агрегатна заявка умножават редовете: всяко стартиране се броеше по веднъж за **всеки** ред в `status_changes` на медията, затова „Стартирана N пъти" беше завишено при медии с поне две промени на статуса (две стартирания и две смени на статуса даваха „4 пъти"). `MAX(started_at)` не се влияеше (максимумът не зависи от дубликати), затова „последно стартирана" винаги е била вярна. Бъг #27 махна сорта „по дата завършване", полето `MarkedAt` и колоната `marked_at` в заявката, с което отпадна и причината за join-а; поправката е **изтриване на join-а**, а не `COUNT(DISTINCT se.id)` — така в заявката, изпълнявана при всяко зареждане на списъка, не остава join, който нищо не ползва. Видимо следствие: след обновяването броят при някои медии е по-малък — това е корекция на показаното число, `start_events` никога не е бил повреден. Регресионният тест `TestMediaStats_StartCountIgnoresStatusChanges` (две стартирания + две смени на статус → 2) е проверен да пада върху стария `stats.go` с 4.

### Защо 🎲 отново изписва избраната медия, а отговорът е „първо редът, после флашът" със `useTemplateFragments` (Итерация 42)
Бъг #27 поиска при стартиране на случайна медия да се изпише коя е — това **обръща решението от Итерация 26** (Бъг #16), което махна флаша. Простото връщане на старото рендиране (флаш, после OOB ред — Итерации 24–25) не стига: проба с истинския `htmx.min.js` (1.9.12) в headless Chromium показа, че при конфигурацията по подразбиране **редът не се обновява при нито една от двете подредби на фрагментите** (при „флаш първи" в `#flash` изтича и текстът на клетките му, при „ред първи" `#flash` остава празен); работеше само отговор с един OOB ред (какъвто беше между Итерации 26 и 41). Следователно **🎲 в Итерации 24–25 не е обновявал реда в браузъра**: Go тестовете проверяваха само тялото на отговора, а e2e тест за 🎲 нямаше. От петте проверени комбинации **и двата фрагмента се разместват само при реда първи + `useTemplateFragments: true`**: отговорът се парсва в `<template>`, където водещият `<tr>` запазва табличния си контекст, а следващият `<span>` остава негов съсед. Затова `RandomNew` рендира `MediaRowOOB`, после `Flash`, а `ListPage` включва настройката с `<meta name="htmx-config" content='{"useTemplateFragments":true}'>` в `<head>`. Пълната таблица на пробата и причината (при настройката по подразбиране htmx избира начина на парсване по **първия таг** на отговора) са в раздел „Находка" на [плана на Итерация 42](Итерации/Итерация%2042%20-%20Бъг%2027%20%283%2B4%29%20случайният%20филм%20се%20изписва%20%2B%20без%20Детайли.md). Без HTMX остава redirect към филтрирания списък, без флаш — както преди.

Настройката важи за цялата страница, но засяга само **частичните** отговори: редовете (водещ `<tr>` — работят), „Няма филми за избор" (`<span>`) и 🎲; живото търсене получава цяла страница (с `<body>`) и се парсва както преди — ревюто провери всеки `hx-*` атрибут на страницата. Затова и подредбата, и настройката са пазени от тестове: `TestRandomNew_HTMX_RowComesBeforeFlash` (отговорът трябва да **започва** с реда), `TestIndex_HtmxConfigUsesTemplateFragments` и e2e `test_random_shows_film_and_updates_row` — единственият, който доказва в браузър, че редът е сменен на място, а `#flash` съдържа само името. Следствие за бъдещи промени: тест на тялото на HTMX отговор не доказва, че браузърът го размества — всеки нов частичен отговор, особено с OOB, се проверява с e2e тест.

### Защо изгледът „Детайли" е махнат изцяло, а таблиците `start_events` и `status_changes` остават (Итерация 42)
Бъг #27 поиска бутонът и изгледът „Детайли" (`ℹ` → `GET /media/:id`) да се махнат. Махането е **пълно**: бутонът, маршрутът (сега отговаря `404`, без пренасочване), `MediaDetail`, `templates/detail.templ`, заявките `GetStartEvents` и `GetStatusChanges` (единственият им ползвател беше изгледът) и техните тестове — недокоснат код без потребител би останал да се поддържа (в Итерация 41 вече се наложи да се променя падащото меню на страница, която така и така отпада). **Таблиците не се пипат.** `start_events` остава с пълната си функция: от нея се смятат „Стартирана N пъти" и „последно стартирана" (виж „Защо UI denormalization (last_started_at, count) се изчислява"). `status_changes` вече не се чете от приложението, но продължава да се пише (`StartMedia`, `RandomNew`, `ChangeStatus`; и миграция 000007 вписва в нея): историята е данни на потребителя, изтриването на таблица е необратимо (миграциите са forward-only — виж „Защо forward-only миграции (без version check)"), а пазенето ѝ струва само няколко десетки KB (виж „Очакван размер на DB файла"); ако изглед за историята се върне, няма да липсват данни. Цената е, че историята на стартиранията и смените на статус вече не се вижда в приложението — достъпна е само през файла на базата или негов backup снапшот (Итерация 36).
