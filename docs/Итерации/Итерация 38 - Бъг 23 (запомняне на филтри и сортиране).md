# Итерация 38 — Бъг 23: запомняне на филтрите и сортирането в базата

## Контекст

[docs/Открити бъгове.md:639](../Открити%20бъгове.md#L639) — **Бъг #23**:

> да се помнят избраните филтри и сортове в базата. при спиране и пускане на сайта/бакенд-а.

Днес цялото състояние на регистъра живее само в URL-а (`status`, `disk`, `sort`, `dir`,
`q`, `trans`, `del`). При спиране и пускане на `.exe`-то браузърът се отваря на голо `/`
и всичко се връща към стойностите по подразбиране — потребителят трябва да прекликва
филтрите наново при всяко пускане.

**Резултат:** последно използваната комбинация се пази в базата (на самия диск, до `.exe`-то)
и голото `/` я възстановява след рестарт.

**Решение на потребителя:** запомня се **и текстът от полето „търси…" (`q`)** — при пускане
списъкът изглежда точно както е оставен, включително активното търсене.

## Проектантски решения

1. **Къде:** нова таблица `ui_prefs` с **един ред** (`id = 1`, `CHECK (id = 1)`), не key-value.
   Състоянието е фиксиран, малък набор от колони — една схема, едно четене, без сериализация.
   Редът се създава от самата миграция, така че `GetUIPrefs` винаги намира ред.
2. **Кога се чете:** запомнените стойности стават **default-и на всеки query параметър**
   поотделно (`c.DefaultQuery("status", prefs.StatusFilter)`), вместо специален случай
   „голо `/`". Всички линкове в лентата и без това носят и седемте параметъра, така че
   изричният URL винаги печели; само липсващият параметър се взима от базата.
3. **Кога се пише:** при всяко успешно `GET /` — включително HTMX заявката на живото
   търсене, която също носи всичките седем параметъра. Записът е един `UPSERT` на един ред.
4. **Грешка в базата не чупи страницата:** при грешка в четенето се ползват старите
   константи по подразбиране; грешка при запис само се логва.
5. **UI не се променя изобщо** — няма нов бутон, няма нови класове; затова тази итерация
   не носи stale-test дълг в шаблонните тестове.

## Промени

### 1. DB — нова таблица

Миграция `internal/db/migrations/000005_add_ui_prefs.{up,down}.sql`:

```sql
CREATE TABLE ui_prefs (
    id            INTEGER PRIMARY KEY CHECK (id = 1),
    status_filter TEXT NOT NULL DEFAULT 'all',
    disk_filter   TEXT NOT NULL DEFAULT 'on',
    sort_filter   TEXT NOT NULL DEFAULT 'name',
    dir_filter    TEXT NOT NULL DEFAULT 'asc',
    q_filter      TEXT NOT NULL DEFAULT '',
    trans_filter  TEXT NOT NULL DEFAULT 'all',
    del_filter    TEXT NOT NULL DEFAULT 'all',
    updated_at    TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

INSERT INTO ui_prefs (id) VALUES (1);
```

Default-ите в схемата съвпадат едно към едно с досегашните `c.DefaultQuery(...)` стойности.

### 2. sqlc заявки — `internal/db/queries.sql`

```sql
-- name: GetUIPrefs :one
SELECT status_filter, disk_filter, sort_filter, dir_filter, q_filter, trans_filter, del_filter
FROM ui_prefs WHERE id = 1;

-- name: SaveUIPrefs :exec
INSERT INTO ui_prefs (id, status_filter, ...) VALUES (1, ?, ...)
ON CONFLICT(id) DO UPDATE SET ... , updated_at = CURRENT_TIMESTAMP;
```

### 3. Handlers — `internal/web/handlers.go`

- Нов метод `loadPrefs(ctx)` → `db.GetUIPrefsRow`; при грешка връща реда с константите по
  подразбиране (`all/on/name/asc///all/all`).
- `Index`: седемте `c.DefaultQuery(...)` вземат default-а от запомнените стойности; след
  разрешаването им — `savePrefs(ctx, ...)` (логва грешка, не прекъсва рендирането).
- `RandomNew` и останалите POST handler-и **не** пипат `ui_prefs` — състоянието се записва
  от заявката към списъка, която така или иначе следва.

### 4. E2E — изолация между тестовете

Понеже сървърът и базата са **общи за цялата pytest сесия**, запомненото състояние вече
изтича между тестовете (напр. `test_filter_disk_toggle_has_both_directions` посещава
`/?disk=all` и следващият тест на голо `/` би получил `disk=all`).

`tests/e2e/conftest.py` получава autouse function-scoped фикстура `reset_prefs`, която преди
всеки тест дърпа веднъж URL с всички default-и, т.е. връща `ui_prefs` към изходното.
